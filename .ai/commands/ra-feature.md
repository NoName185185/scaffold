# Команда: ra-feature — конвейер разработки фичи

Ты — оркестратор. Ведёшь фичу от идеи до DevLog. Каждого агента запускай в чистом контексте (субагент), передавая ему только указанные входы — пути к файлам, не пересказ содержимого. Инструкции агентов — в `.ai/agents/<имя>.md`.

## Аргументы

- Описание фичи или хотелки (свободный текст), ЛИБО путь к существующему `EpicSummary.md` + номер этапа.
- Опционально номер: `TZ<эпик>_<фича>` (если нет — придумай следующий свободный по `Doc/Features/`).

## Схема

```
эпик → спека → [ЧЕЛОВЕК одобряет] → план кода → код → ревью (≤2)
→ план тестов → тесты → ревью (≤2) → devlog
провал 2-го ревью (кода или тестов) → devlog (INTERRUPTED) → возврат к одобрению спеки
```

## Шаги

### Шаг 1. Эпик (пропускается для малых фич)

Если фича маленькая (один модуль, понятный объём) — пропусти. Иначе запусти `epic-writer`.

### Шаг 2. Спецификация

Запусти `spec-writer` (вход: EpicSummary.md + этап, либо описание фичи; при повторном заходе — замечания человека и DevLog прошлой попытки).

### Шаг 3. ОСТАНОВКА: одобрение человеком

Покажи человеку резюме спеки и путь к `Spec.md`. Жди явного ответа.
- Одобрил → проставь в Spec.md статус APPROVED, дальше конвейер идёт БЕЗ остановок.
- Есть правки → верни spec-writer с замечаниями (версия +1), снова шаг 3.

### Шаг 4. План кода

Запусти `code-planner` (вход: Spec.md). Если вернул блокирующие вопросы вместо плана — это возврат к шагу 3 (покажи вопросы человеку).

### Шаг 5. Код + ревью (максимум 2 попытки)

1. Запусти `developer` (вход: Spec.md, CodePlan.md).
2. Запусти `reviewer` в режиме `code` (вход: Spec.md, CodePlan.md, отчёт developer, номер попытки).
3. APPROVED → шаг 6.
4. CHANGES_REQUESTED, попытка 1 → верни developer только с замечаниями ревьюера, затем повтор ревью (попытка 2).
5. CHANGES_REQUESTED, попытка 2 → ПРЕРЫВАНИЕ: шаг 8 с итогом INTERRUPTED, затем шаг 3 (человеку — «Причина для человека» из вердикта).

### Шаг 6. План тестов

Запусти `test-planner` (вход: Spec.md, CodePlan.md, отчёт developer).

### Шаг 7. Тесты + ревью (максимум 2 попытки)

Аналогично шагу 5: `test-developer` → `reviewer` в режиме `test`. Провал 2-й попытки → шаг 8 (INTERRUPTED) → шаг 3.

### Шаг 8. DevLog

Запусти `devlog-writer` (вход: папка фичи, отчёты и вердикты всех этапов). Покажи человеку резюме. Готово — человек читает и коммитит сам.

## Правила оркестратора

- Единственные остановки на человека: шаг 3 и прерывание после 2 проваленных ревью. Больше нигде не спрашивай.
- Не выполняй работу агентов сам — только запуск, передача путей, разбор результатов.
- Все счётчики попыток веди сам и явно сообщай агентам номер попытки.
- Между шагами ничего не коммить в git.
- Перед любым commit/push: `git fetch origin staging` и `git pull origin staging` (на feature-ветке — `git merge origin/staging`). Правило также в `.cursor/rules/git-staging-sync.mdc`.
