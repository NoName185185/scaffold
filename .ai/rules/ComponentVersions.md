# Правило: semver-версии компонентов RUBA AI OS

Компоненты с независимыми версиями `MAJOR.MINOR.PATCH` и датой `YYYY-MM-DD`:

| Компонент | Источник |
|-----------|----------|
| bridge | `BRIDGE_VERSION` / `BRIDGE_VERSION_DATE` в `bitrix/public/local/components/ruba/api/product.php` |
| backend | `BACKEND_VERSION` / `BACKEND_VERSION_DATE` в `backend/app/version.py` |
| webapp | `version` / `versionDate` в `webapp/package.json` (runtime: публичный `GET /version.json`) |

Общей app-version поверх трёх **нет**.

## Политика bump

| Уровень | Кто | Когда |
|---------|-----|--------|
| **PATCH** | агент сам | правка уже существующего поведения (багфикс, уточнение) без новой фичи → `PATCH + 1`; обновить дату |
| **MINOR** | агент **спрашивает** человека | только если реально добавляется новая функциональность (обратно совместимая). Не спрашивать «patch или minor?» на каждый дифф |
| **MAJOR** | только человек | агент MAJOR **не** поднимает |

Дополнительно:

- Bump только компонента(ов), файлы которых реально менялись в диффе.
- Косметика только в комментариях / чистое форматирование без смены поведения — bump не обязателен; при сомнении — PATCH.
- Причину bump фиксировать в `DevLog.md` фичи (например «backend → 0.1.1 (дата)», «мост → 0.4.1 (дата)»).
- Автотест **не** решает «нужно ли было bump’ать»; ловит формат. «Забыли bump» — процесс ревью.

## Ревью

Смысловой дифф компонента без обязательного bump версии/даты этого компонента → **CHANGES_REQUESTED**.

Для моста детали также в `BitrixBridge.md` (формат — semver, не монотонный счётчик).
